# AGENTS.md — правила работы Codex с OptiScaler

Этот файл задаёт постоянные правила для Codex и других автономных агентов, работающих с данным репозиторием.

Основная цель этих правил — получать небольшие, проверяемые и архитектурно совместимые изменения без скрытых допущений, случайных регрессий и загрязнения базовой ветки.

---

## 1. Главный принцип работы

Работай по циклу:

**понять → проверить исходное состояние → спланировать → изменить → немедленно проверить → только затем двигаться дальше.**

### ОБЯЗАТЕЛЬНО: самопроверка после каждого шага

После **каждого завершённого шага** необходимо проверить себя до перехода к следующему шагу.

Под шагом понимается любое законченное действие, которое может повлиять на результат, например:

- изменение файла;
- добавление или удаление файла;
- рефакторинг функции или класса;
- изменение hook/interception-логики;
- изменение build-настроек;
- изменение конфигурации;
- обновление submodule;
- запуск команды, меняющей состояние репозитория;
- создание commit/ветки;
- исправление ошибки компиляции;
- изменение графического ресурса, его lifetime, state или synchronization;
- изменение API-вызова DLSS/NVNGX/Streamline/FSR/XeSS/OptiFG.

После каждого такого шага выполни подходящую проверку и убедись, что ожидаемый результат действительно достигнут.

Минимальная самопроверка должна отвечать на вопросы:

1. **Что именно я только что изменил?**
2. **Соответствует ли фактический результат тому, что я хотел получить?**
3. **Не затронул ли я лишние файлы, код или поведение?**
4. **Не нарушил ли я существующие инварианты и архитектуру?**
5. **Есть ли локальная проверка, которую можно выполнить прямо сейчас?**
6. **Нет ли новой ошибки, warning, конфликтующего состояния или неучтённого edge case?**

Если проверка не пройдена — **не продолжай следующий шаг**. Сначала найди причину, исправь проблему и повтори проверку.

Никогда не считай действие успешным только потому, что команда была запущена или код выглядит правдоподобно.

## 2. Поведение при неопределённости

Не додумывай устройство проекта по названию файла, класса или функции.

Если для решения задачи важна архитектура, сначала найди реальный call flow и фактические владельцы данных.

Разделяй:

- подтверждённый факт из кода;
- предположение;
- гипотезу для проверки;
- вывод, подтверждённый build/test/runtime evidence.

Если остаётся существенная неопределённость, явно сообщи о ней.

Не скрывай ошибки, неудачные эксперименты, warnings или непроверенные участки.

## 3. Репозиторий и базовая ветка

Основная рабочая база этого форка:

`dlss-neural-rendering`

Эта ветка рассматривается как **базовая**.

### Правила Git

- Не выполняй обычную разработку напрямую в `dlss-neural-rendering`.
- Если Codex запущен в отдельном worktree, работай внутри предоставленного worktree и не переключай ветки в основном checkout пользователя.
- Не изменяй соседние worktree.
- Не удаляй worktree пользователя.
- Не выполняй `git reset --hard`, `git clean -fdx`, force-push и другие потенциально разрушительные операции без прямого запроса пользователя.
- Не переписывай чужую историю.
- Не откатывай существующие пользовательские изменения, которые не относятся к текущей задаче.
- Перед началом изменений проверь `git status`.
- После каждого логического набора изменений снова проверь `git status` и diff.

Если для сохранения результата нужна отдельная ветка, используй понятное имя вида:

`codex/<короткое-описание-задачи>`

Например:

- `codex/fix-dlss-init`
- `codex/streamline-fg-validation`
- `codex/dx12-resource-state-fix`

Не создавай commit, push или Pull Request, если это не требуется текущей задачей или пользователь явно этого не попросил.

## 4. Фактическая build-база проекта

Проект ориентирован прежде всего на Windows и Visual Studio 2022.

Основной solution:

`OptiScaler.sln`

В solution присутствуют как минимум:

- `OptiScaler` — `OptiScaler/OptiScaler.vcxproj`;

Поддерживаемые конфигурации solution включают:

- Debug;
- Release;
- ReleaseDebug;

и платформы x64/x86.

Для основной разработки по умолчанию предпочитай **x64**, если задача прямо не относится к Win32/x86.

Не меняй toolset, Windows SDK, language standard или структуру solution без реальной необходимости.

## 5. Зависимости и submodules

Перед сборкой или анализом ошибок include/link сначала проверь состояние зависимостей.

Репозиторий использует git submodules, включая зависимости в `external/`.

Перед попыткой исправлять якобы отсутствующий header/library:

1. проверь `.gitmodules`;
2. выполни `git submodule status --recursive`;
3. убедись, что нужный submodule действительно инициализирован;
4. только после этого делай вывод, что зависимость отсутствует.

Если среда разрешает сетевой доступ и это требуется, допустима команда:

`git submodule update --init --recursive`

После неё **обязательно проверь результат** повторным `git submodule status --recursive` и убедись, что не произошло неожиданного изменения pinned revisions.

Не обновляй версии submodules до новых upstream-коммитов без явной причины задачи.

Не vendor'и сторонний проект в дерево исходников, если существующая архитектура использует submodule или другой механизм зависимостей.

## 6. ВАЖНО: `setup_windows.bat` — не build/setup исходников

Корневой `setup_windows.bat` предназначен для установки готового OptiScaler в папку игры.

Он **не является скриптом подготовки исходного репозитория или сборки**.

Не запускай его как команду setup/build при разработке исходников.

Не модифицируй его только ради того, чтобы «починить сборку», если задача не относится непосредственно к игровому installer/setup workflow.

## 7. Сборка

Перед сборкой:

1. проверь текущий worktree/branch;
2. проверь `git status`;
3. проверь submodules;
4. убедись, что используешь Developer Command Prompt/PowerShell для Visual Studio 2022 либо корректно найденный MSBuild;
5. зафиксируй, какую конфигурацию собираешь.

Предпочтительный базовый вариант проверки изменений для x64:

`msbuild OptiScaler.sln /m /p:Configuration=ReleaseDebug /p:Platform=x64`

Если задача относится к release-specific поведению, дополнительно проверь:

`msbuild OptiScaler.sln /m /p:Configuration=Release /p:Platform=x64`

Если `msbuild` отсутствует в PATH, сначала найди установленный Visual Studio/MSBuild штатным способом (например, через `vswhere`) вместо того, чтобы жёстко прописывать путь конкретного компьютера.

### После каждой сборки обязательно

- проверь exit code;
- просмотри ошибки и warnings, относящиеся к изменённому коду;
- не называй build успешным, если команда завершилась с ошибкой;
- не скрывай warnings, возникшие из-за твоего изменения;
- если полный solution build невозможен из-за среды, явно укажи причину и выполни максимально близкую доступную проверку.

Не «лечи» ошибку компиляции отключением warning/error, удалением проверки или закомментированием функциональности, если не доказано, что именно это является корректным исправлением.

## 8. Архитектурный принцип OptiScaler

Сохраняй существующую концепцию middleware:

**Input → OptiScaler → Output**

То же относится к Frame Generation, где input и output также являются отдельными понятиями.

Перед добавлением нового пути сначала выясни:

- какой существующий Input наиболее близок по контракту;
- какой общий abstraction/interface уже существует;
- где выбирается Output/backend;
- кто владеет feature instance/context;
- где происходит resource translation;
- где происходит API-specific dispatch;
- где хранится конфигурация;
- где реализованы lifecycle/reset/recreate paths.

### Не создавай параллельную архитектуру без необходимости

Если существующий механизм можно расширить, предпочитай расширение существующего abstraction вместо нового независимого hook/framework/backend manager.

Не дублируй уже существующую инфраструктуру только потому, что так быстрее сделать proof-of-concept.

Для эксперимента допускается локальный PoC, но он должен быть чётко отделён от production-кода и не маскироваться под окончательное решение.

---

## 9. Не ломай существующие backend/input пути

Без прямого требования задачи не удаляй и не упрощай за счёт потери функциональности существующие пути:

- DLSS / NVNGX;
- Streamline;
- FSR;
- XeSS;
- OptiFG;
- FSR Frame Generation;
- XeSS Frame Generation;
- существующие DX11/DX12/Vulkan integration paths.

Изменение одного backend не должно незаметно менять поведение другого backend.

Если общий код всё же требуется изменить, сначала перечисли потенциально затрагиваемые consumers и после изменения проверь их отдельно.

---

## 10. Правила для DLSS / NVNGX / Streamline

Перед изменением DLSS/NVNGX/Streamline-кода обязательно проследи полный lifecycle:

1. discovery/loading;
2. initialization;
3. capability/query path;
4. feature creation;
5. per-frame parameter update;
6. evaluate/dispatch;
7. reset/recreate;
8. shutdown/destruction;
9. device lost / swapchain recreate / resolution change, если применимо.

Не смешивай NVNGX и Streamline concepts, если код проекта намеренно разделяет эти пути.

При исправлении одного из путей проверь, что fallback/alternative path не стал недоступен.

Не добавляй proprietary NVIDIA DLL, SDK binary или redistributable в Git.

Не подменяй реальную интеграцию копированием закрытых/бинарных компонентов.

---

## 11. Правила для DX11 / DX12 / Vulkan hooks

Перед изменением hook-кода установи:

- что именно перехватывается;
- на каком уровне API;
- кто установил hook;
- сколько раз он может устанавливаться;
- как предотвращается recursion/re-entry;
- кто владеет original function pointer;
- как происходит unhook/shutdown;
- какие потоки могут попасть в hook;
- есть ли риск device/swapchain recreation.

Не устанавливай второй независимый hook на ту же точку, не доказав совместимость с существующим.

Не меняй порядок hooks без анализа side effects.

Для COM-объектов следи за ownership и `AddRef`/`Release`.

Не удерживай raw pointer на ресурс дольше гарантированного lifetime.

Не предполагай thread-safety — проверь её по фактическому коду.

---

## 12. Проверка графических ресурсов

Любое изменение, связанное с upscaling/frame generation/render interception, должно учитывать не только наличие texture pointer, но и **семантику ресурса**.

Для каждого используемого ресурса при необходимости проверь:

- API: DX11/DX12/Vulkan;
- format;
- dimensions;
- render resolution и output resolution;
- resource state/layout;
- ownership/lifetime;
- synchronization;
- command queue / command list context;
- descriptor lifetime;
- array/mip/subresource;
- UAV/SRV/RTV compatibility;
- aliasing;
- resize/recreation path.

Для temporal upscaler/FG отдельно проверь:

- input color;
- output color;
- depth;
- motion vectors;
- motion-vector scale/units;
- jitter offset;
- jitter convention/sign;
- exposure;
- pre-exposure, если используется;
- render size;
- display size;
- reset flag;
- frame index;
- camera cut;
- reversed-Z / depth convention;
- near/far semantics, если требуются API;
- reactive/transparency masks, если применимо;
- HUD/UI composition point для FG.

Не подключай ресурс к DLSS/FG только потому, что его формат «похож». Подтверди его назначение по producer/consumer chain.

---

## 13. Resource states и синхронизация DX12

Для DX12-изменений особенно внимательно проверяй:

- состояние ресурса до вызова;
- required state внутри backend;
- состояние после вызова;
- кто отвечает за transition barrier;
- кто отвечает за UAV barrier;
- fence/queue synchronization;
- выполнение на правильной command queue;
- отсутствие использования command list после close/submit;
- отсутствие использования stale resource после resize/recreate.

После изменения barrier/state logic найди все соседние consumers этого ресурса.

Не исправляй state mismatch глобальным переводом всего в `COMMON`/`GENERIC_READ`, если это не подтверждено контрактом API.

---

## 14. Lifetime, ownership и состояние

Для новых объектов всегда определяй владельца.

Ответь до реализации:

- кто создаёт объект;
- кто уничтожает объект;
- когда он инвалидируется;
- переживает ли он resize;
- переживает ли он device recreation;
- может ли использоваться несколькими потоками;
- нужен ли mutex/atomic;
- может ли callback прийти после shutdown.

Предпочитай существующие RAII-механизмы проекта.

Не добавляй глобальное mutable state, если можно привязать состояние к уже существующему context/device/backend object.

---

## 15. Конфигурация и обратная совместимость

Не ломай существующий `OptiScaler.ini` и поведение текущих параметров без прямой необходимости.

При добавлении новой опции:

- используй существующий механизм конфигурации;
- выбери безопасное значение по умолчанию;
- сохрани поведение старых конфигов;
- не переиспользуй старый ключ с новой несовместимой семантикой;
- при необходимости обнови соответствующую документацию.

После изменения конфигурации проверь как минимум:

- ключ отсутствует;
- ключ задан валидным значением;
- некорректное значение не приводит к неопределённому поведению.

---

## 16. Логирование и диагностика

Используй существующую logging infrastructure проекта.

Не добавляй случайные `printf`, MessageBox или постоянный noisy logging, если проект уже использует централизованный logger.

Новая диагностическая запись должна помогать ответить на конкретный вопрос.

Не логируй секреты, персональные пути пользователя или большие бинарные данные.

При обработке ошибки лог должен содержать достаточно контекста, чтобы отличить:

- unsupported;
- initialization failure;
- resource mismatch;
- backend failure;
- fallback;
- user configuration issue.

---

## 17. Обработка ошибок

Не игнорируй HRESULT/result/status только ради продолжения выполнения.

Для нового API-вызова выясни:

- какие результаты являются success;
- какие являются expected/unsupported;
- какие требуют fallback;
- какие требуют reset/recreate;
- какие являются fatal для данного feature, но не для всего OptiScaler.

Не превращай recoverable backend failure в crash всего процесса без необходимости.

Не превращай реальную ошибку в silent success.

---

## 18. Стиль изменений

Соблюдай существующий стиль ближайшего кода.

Не выполняй массовое форматирование файлов, не относящееся к задаче.

Не переименовывай сотни символов вместе с небольшим bugfix без необходимости.

Не смешивай в одном изменении:

- функциональный fix;
- большой refactor;
- stylistic cleanup;
- переименование;
- изменение build system.

Если refactor необходим для fix, сначала минимально изолируй причину и объясни, почему refactor действительно нужен.

---

## 19. Минимальный diff

Предпочитай наименьшее изменение, которое корректно решает установленную причину проблемы.

Перед завершением задачи выполни:

`git diff --check`

Затем внимательно просмотри полный diff.

Проверь:

- нет ли accidental formatting churn;
- нет ли debug-кода;
- нет ли временных комментариев;
- нет ли hardcoded локальных путей;
- нет ли бинарников;
- нет ли чужих изменений;
- нет ли изменения поведения, не относящегося к задаче.

---

## 20. Исследовательские задачи

Если пользователь попросил **только анализ**, не изменяй код.

При архитектурном исследовании сначала подготовь карту:

- relevant files;
- classes/structs;
- key functions;
- initialization path;
- per-frame call flow;
- resource flow;
- ownership;
- backend selection;
- cleanup/reset path;
- точки расширения.

Не предлагай архитектуру, пока не проследил существующий механизм достаточно глубоко.

---

## 21. Bugfix workflow

Для исправления ошибки используй следующий порядок:

1. Зафиксируй симптом.
2. Найди минимальный воспроизводимый call path по коду/logs.
3. Найди непосредственную причину.
4. Проверь, не является ли она следствием более ранней ошибки.
5. Сформулируй ожидаемый инвариант.
6. Сделай минимальный fix.
7. **Сразу проверь fix.**
8. Проверь соседние paths.
9. Собери затронутый проект/solution.
10. Просмотри diff.
11. Только после этого считай задачу законченной.

После **каждого пункта** сделай короткую внутреннюю самопроверку результата. Не выполняй весь список «вслепую» до конца.

---

## 22. Feature workflow

Для новой функциональности:

1. Найди существующую ближайшую abstraction.
2. Определи interface/contract.
3. Определи data/resource requirements.
4. Определи lifecycle.
5. Определи compatibility/fallback behavior.
6. Спроектируй минимальную интеграцию.
7. Реализуй по небольшим шагам.
8. **После каждого шага проверяй компиляцию/локальные инварианты там, где это разумно.**
9. После завершения выполни полную релевантную сборку.
10. Проверь итоговый diff и регрессии.

Не начинай с большого переписывания системы, если задача может быть реализована расширением существующего механизма.

---

## 23. Тестирование

Не выдумывай наличие test suite, которого нет.

Если автоматических тестов для изменённого компонента нет, используй сочетание:

- compile validation;
- static inspection;
- targeted assertions/checks, если они уместны и остаются частью корректного production-кода;
- существующее logging;
- известный runtime reproduction plan.

Не утверждай, что runtime bug исправлен окончательно, если удалось подтвердить только компиляцию.

Различай в отчёте:

- `проверено сборкой`;
- `проверено статически`;
- `проверено runtime`;
- `не удалось проверить в текущей среде`.

---

## 24. Безопасность репозитория

Никогда не коммить:

- generated binaries;
- build output;
- `.dll/.exe/.pdb` только потому, что они появились после локальной сборки;
- игровые файлы;
- proprietary NVIDIA binaries;
- credentials;
- tokens;
- API keys;
- cookies;
- private certificates;
- machine-specific absolute paths;
- локальные IDE/user settings, если они не являются частью проекта.

Перед commit/push обязательно просмотри список staged files.

---

## 25. Никаких скрытых обходов

Запрещено выдавать обход проблемы за её исправление без явного объяснения.

Примеры нежелательного поведения:

- отключить failing path;
- всегда возвращать success;
- подавить exception/error;
- отключить warning;
- force-enable capability без проверки;
- hardcode конкретную игру/GPU без архитектурной причины;
- пропустить synchronization;
- добавить sleep вместо исправления race;
- отключить cleanup, чтобы избежать crash;
- намеренно утечь ресурс, чтобы избежать use-after-free.

Если временный workaround действительно нужен для диагностики, пометь его как экспериментальный и не представляй как финальное решение.

---

## 26. Особое правило для потенциально рискованных изменений

Перед изменением следующих областей сначала составь краткий план и проверь затрагиваемые paths:

- DLL entry/init/shutdown;
- global hooks;
- swapchain hooks;
- D3D device/queue interception;
- resource state management;
- NVNGX initialization;
- Streamline initialization;
- frame generation dispatch;
- overlay/input interception;
- configuration migration;
- shared global state.

После такого изменения обязательны:

1. локальная проверка изменённого участка;
2. build;
3. просмотр всего diff;
4. проверка минимум одного соседнего/альтернативного path по коду.

---

## 27. Приоритет фактов над догадками

Если комментарий противоречит коду, проверь историю/usage и установи фактическое поведение.

Если документация противоречит реализации, не выбирай автоматически одну сторону — зафиксируй расхождение.

Если API contract неизвестен, найди используемый в репозитории SDK/header/documented contract прежде чем менять параметры вызова.

Не придумывай значения enum/flags/feature IDs.

---

## 28. Что делать после каждого редактирования файла

После значимого редактирования конкретного файла:

1. перечитай изменённый участок целиком, а не только добавленные строки;
2. проверь surrounding control flow;
3. проверь includes/types/namespaces;
4. проверь ownership/lifetime для новых объектов;
5. проверь error path;
6. проверь, не появился ли unreachable/dead code;
7. посмотри локальный diff файла;
8. если изменение компилируемо изолированно — выполни доступную проверку;
9. только затем переходи к следующему файлу.

Это правило является обязательным воплощением принципа **«проверять себя после каждого шага»**.

---

## 29. Что делать после исправления compiler error

После каждого исправленного compiler/linker error:

1. убедись, что исправлена причина, а не только текст ошибки;
2. запусти сборку снова;
3. проверь, исчезла ли именно эта ошибка;
4. проверь, не появились ли новые ошибки из-за обходного решения;
5. не переходи дальше, пока текущее исправление не подтверждено.

Не накапливай десяток непроверенных исправлений между build-запусками, если ошибки можно проверять последовательно.

---

## 30. Финальная проверка перед завершением задачи

Перед финальным ответом обязательно выполни максимально возможный набор:

1. `git status`;
2. `git diff --check`;
3. полный просмотр `git diff`;
4. релевантный build;
5. проверка созданных/удалённых файлов;
6. проверка отсутствия бинарников и секретов;
7. проверка того, что задача пользователя действительно решена;
8. проверка того, что не заявлено больше, чем реально подтверждено.

Если какая-либо проверка не выполнена, явно укажи это и причину.

---

## 31. Формат итогового отчёта

В конце задачи дай короткий, фактический отчёт:

### Что изменено
Перечисли ключевые изменения и файлы.

### Почему
Укажи найденную причину проблемы или архитектурное основание изменения.

### Как проверено
Укажи точные команды/проверки и их результат.

### Что не проверено
Отдельно перечисли то, что требует runtime/game/GPU/SDK environment и не было доступно.

### Риски / следующие шаги
Укажи только реальные оставшиеся риски, без выдуманных проблем.

## 32. Критерий готовности

Задача не считается завершённой, пока одновременно не выполнено следующее:

- причина или требование поняты;
- изменение минимально и относится к задаче;
- после **каждого шага** выполнена соответствующая самопроверка;
- итоговый diff просмотрен;
- доступная сборка/проверка выполнена;
- ошибки проверки не скрыты;
- существующая архитектура и альтернативные backend paths не были случайно сломаны;
- итоговый отчёт отделяет доказанное от непроверенного.

Если хотя бы один из этих пунктов не выполнен — продолжай работу либо явно сообщи, почему дальнейшая проверка невозможна в текущей среде.

---

## 33. АБСОЛЮТНОЕ ПРАВИЛО: перепроверять себя всегда

Самопроверка обязательна **абсолютно всегда**, а не только при программировании, аудите, сборке или изменении Git-состояния.

Любое действие, вывод, предположение, поиск, чтение, изменение, команда, решение, сравнение, классификация результата или финальное утверждение должно сопровождаться подходящей проверкой до того, как оно будет принято как корректное.

Нельзя пропускать самопроверку потому, что действие кажется простым, очевидным, повторяющимся, низкорисковым или уже выполнялось ранее.

Перед переходом к следующему действию необходимо убедиться как минимум в следующем:

1. действие действительно было выполнено;
2. получен именно ожидаемый результат;
3. результат относится к нужному объекту, файлу, ветке, конфигурации или среде;
4. не возникло скрытого побочного эффекта;
5. вывод подтверждается фактом, а не предположением;
6. если доступна независимая или повторная проверка — она выполнена там, где это разумно.

При работе с инструментами нельзя считать операцию успешной только по факту отправки команды. Необходимо прочитать и проверить фактический ответ инструмента.

При чтении нельзя считать информацию найденной или отсутствующей без проверки соответствующего источника и области поиска.

При изменении нельзя считать исправление корректным без проверки результата изменения.

При повторном действии нельзя механически доверять предыдущему результату — необходимо учитывать, что состояние могло измениться.

Если результат невозможно полностью проверить, обязательно раздели:

- что подтверждено;
- чем подтверждено;
- что осталось непроверенным;
- почему это невозможно проверить в текущей среде.

Никогда не выдавай предположение, частичную проверку или косвенный признак за полностью подтверждённый результат.

Это правило имеет глобальный характер и действует **при любом действии и при любом раскладе на протяжении всей задачи**.

## 34. Полный аудит: ни одного пропущенного файла, участка или символа

Если пользователь использует слово **«аудит»** или прямо просит полный/исчерпывающий аудит, это означает **полный последовательный аудит всей заданной области**, а не выборочный code review, поиск типичных ошибок или анализ наиболее важных файлов.

### 34.1. Нельзя пропускать ничего в заданном scope

В рамках области аудита запрещено намеренно или случайно пропускать:

- отдельные файлы;
- каталоги;
- исходники;
- headers;
- build/configuration files;
- scripts;
- документацию, если она входит в scope;
- generated/third-party/submodule content, если пользователь включил его в scope;
- строки;
- блоки;
- ветви условной компиляции;
- комментарии, если они могут влиять на понимание/контракт;
- отдельные символы в текстовых файлах.

Для текстового файла полный аудит означает чтение файла **целиком от первого до последнего символа** в пределах доступного представления файла.

Нельзя заменять это:

- поиском по ключевым словам;
- grep/ripgrep-only анализом;
- просмотром только найденных совпадений;
- выбором «подозрительных» файлов;
- чтением только функций, которые кажутся релевантными;
- чтением diff вместо полного текущего файла;
- предположением, что типовой или похожий файл можно не читать.

Поиск допустим как вспомогательный инструмент навигации, но **никогда не заменяет полное чтение** при полном аудите.

### 34.2. Перед аудитом создай контрольный список

До содержательного анализа сначала построи полный inventory заданной области аудита.

Зафиксируй:

- корень/scope аудита;
- полный список файлов;
- количество файлов;
- исключения, только если они явно разрешены пользователем;
- отдельно submodules, symlinks, generated files, binaries и файлы, которые невозможно прочитать обычным способом.

Этот inventory является контрольным списком аудита.

Во время работы каждый файл должен иметь явный статус, например:

- `[ ] не начат`;
- `[~] читается`;
- `[x] прочитан полностью`;
- `[v] проанализирован`;
- `[vv] перепроверен`;
- `[!] не удалось полностью проверить — указана причина`.

Не помечай файл как прочитанный, проверенный или перепроверенный заранее.

### 34.3. Если файл читается частями — контролируй диапазоны

Если из-за размера или ограничений инструмента файл приходится читать несколькими диапазонами:

1. зафиксируй полный размер/диапазон, если он доступен;
2. записывай уже прочитанные диапазоны;
3. обеспечь непрерывное покрытие от начала до конца;
4. проверь отсутствие дыр и непреднамеренных перекрытий;
5. только после покрытия всего файла помечай его как прочитанный полностью.

Например, чтение `1–200`, затем `401–600` **не является полным чтением**, пока диапазон `201–400` не прочитан.

Если инструмент обрезал результат, файл остаётся непроверенным до получения недостающей части.

### 34.4. После каждого файла обязательна локальная самопроверка

После завершения чтения каждого файла:

1. убедись, что прочитан весь файл;
2. сверь фактический диапазон/размер;
3. пометь статус в checklist;
4. зафиксируй найденные проблемы отдельно от ещё непроверенных гипотез;
5. проверь связи файла с уже прочитанными producers/consumers/callers/callees;
6. только затем переходи к следующему файлу.

### 34.5. Ошибка чтения не разрешает пропустить файл

Если файл нельзя прочитать из-за:

- размера;
- кодировки;
- бинарного формата;
- повреждения;
- отсутствующего submodule;
- ошибки инструмента;
- permission/access issue;
- unsupported representation;

не исключай его молча.

Оставь его в checklist со статусом `[!]`, укажи точную причину и используй подходящий альтернативный способ проверки, если он доступен.

Пока такой файл не проверен полностью, нельзя утверждать, что полный аудит всего scope завершён.

### 34.6. Повторная инвентаризация обязательна

После первого полного прохода повторно получи список файлов в том же scope и сравни его с исходным inventory.

Необходимо подтвердить:

- количество файлов совпадает либо различие объяснено;
- не появился новый файл;
- ни один исходный файл не потерян;
- каждый файл имеет финальный статус;
- нет файлов, случайно оставшихся в состоянии `не начат` или `читается`.

Если во время аудита репозиторий изменился, зафиксируй это и заново определи, какой snapshot фактически был проаудирован.

### 34.7. Финальная сверка полноты аудита

Перед заявлением о завершении аудита сформируй контрольную сводку:

- файлов ожидалось: `N`;
- файлов прочитано полностью: `N1`;
- файлов проанализировано: `N2`;
- файлов перепроверено: `N3`;
- файлов непроверено/частично проверено: `N4`;
- причины для каждого элемента `N4`.

Для действительно завершённого полного аудита должно выполняться:

`N = N1 = N2 = N3` и `N4 = 0`, если пользователь не разрешил конкретные исключения.

Если это условие не выполнено, запрещено писать «полный аудит завершён» или эквивалентное утверждение.

### 34.8. Перепроверка результатов аудита

После завершения первого анализа необходимо отдельно перепроверить найденные выводы:

- повторно открыть места, на которых основаны существенные findings;
- проверить surrounding context;
- проверить callers/callees или producers/consumers, когда вывод зависит от взаимодействия;
- проверить, что finding относится к текущей версии файла;
- отделить подтверждённую проблему от потенциального риска;
- убрать false positive, если повторная проверка его не подтверждает.

Аудит считается качественным только когда проверена не только **полнота чтения**, но и **корректность выводов**.

### 34.9. Checklist должен сохраняться на протяжении всего аудита

Не держи состояние полного аудита только «в голове».

Используй явный рабочий список/таблицу/трекер и обновляй его по мере продвижения.

Минимально он должен позволять в любой момент ответить:

- какие файлы существуют в scope;
- какие уже прочитаны полностью;
- какие проанализированы;
- какие перепроверены;
- какие ещё не начаты;
- какие невозможно проверить и почему.

При большом репозитории допустимо разбивать checklist по каталогам, но итоговая сводка должна покрывать весь scope без разрывов.

### 34.10. Аудит и изменения — разные режимы

Если пользователь попросил именно аудит без исправлений, не меняй код во время аудита.

Сначала заверши и перепроверь аудит, затем выдай findings.

Если пользователь одновременно просит аудит и исправления, сначала зафиксируй baseline и полный inventory, затем веди отдельно:

- состояние до исправлений;
- findings;
- выполненные изменения;
- повторную проверку изменённых файлов;
- финальную проверку всего затронутого scope.

Нельзя допустить, чтобы изменение файлов во время аудита разрушило возможность доказать полноту первоначального прохода.

---

## 35. Усиленный критерий готовности после аудита

Если задача являлась аудитом, к общим критериям готовности дополнительно обязательны:

- сформирован полный inventory scope;
- каждый файл имеет отслеживаемый статус;
- каждый текстовый файл прочитан полностью без пропущенных диапазонов;
- результаты чтения перепроверены;
- inventory повторно построен и сверен;
- все findings повторно проверены по исходникам;
- явно указаны любые технически непроверяемые элементы;
- итоговая сводка подтверждает полноту.

Если хотя бы один файл, диапазон или обязательный элемент scope остаётся непрочитанным или непроверенным, полный аудит **не завершён**.
